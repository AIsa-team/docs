## 面临的问题

智能体在任务执行过程中对付费能力的需求日益增加：例如数据扩充查询、深度研究报告或计划外的补充数据集。如果缺乏控制，“选择工具”会悄然演变成“直接花钱”，而一次超时就可能导致重复扣费。理想的状态是让智能体在购买前先获取报价、将支出严格限制在批准的上限内、仅执行一次、同时核验扣费与交付结果，并在不泄露机密的前提下留下完整的审计记录。

## 提示词

当 AIsa [通过 MCP 连接](/zh/agent-quickstart)后，将此提示词提供给你的智能体：

```txt wrap
任务：<你需要完成的事项>。整项任务的预算：<你批准的预算>。在任何付费调用前先询问我；超过 <你的阈值> 时，必须等待我明确同意。
每个付费步骤的流程：(1) 使用 AIsa `search` 查找 operation；(2) 使用 `batch_quote` 获取该调用的准确报价；(3) 向我展示 operation、参数、报价费用以及剩余预算；(4) 在我批准后，使用 `batch_use` 执行该调用一次。
如果报价缺失或失败，或者端点没有文档记录的最大值，请告知我，不要在固定预算下运行。如果 operation 或参数发生变化，必须重新报价。
在遇到超时或结果不明确时，绝不自动重试付费调用：先检查用量并向我汇报。
在结束时，向我提供一份审计表格：步骤 | operation | 报价 | 批准上限 | 结算费用（或 "unknown"）| 结果是否核验？
```

## 所用 API 与 Skill

通过 MCP，你的智能体可以通过 `https://mcp.aisa.one/mcp` 上的几个元工具访问各项 operation：`search`、`list_categories`、`get_details` 和 `batch_quote` 均免费；`batch_use`（单次最多 20 个调用）按次计费。

| 步骤 | 智能体调用的内容 | 参考文档 |
| --- | --- | --- |
| 选择 | 通过 `search` / `list_categories` 寻找满足需求的最小 operation | [通过 MCP 连接](/zh/agent-quickstart) |
| 预估 | 传入具体调用执行 `batch_quote`：仅返回预估费用而不实际运行任何内容 | [先报价、再审核、后执行](/zh/guides/pricing#先报价、再审核、后执行) |
| 授权 | 你的策略层，以及在超过阈值时由人工介入 | [安全与隐私](/zh/guides/security) |
| 执行 | 获得批准后，使用相同的调用执行 `batch_use` | [工作原理](/zh/how-it-works) |
| HTTP 等效方案 | `X-AISA-Cost-Mode: quote`，随后使用 `X-AISA-Max-Price-USD` | [计费与额度](/zh/guides/pricing) |
| 支付核验 | 余额、结算费用元数据、用量 | [额度余额](/zh/api-reference/credits-balance)、[用量](/zh/guides/dashboard/overview#用量) |
| 处理拒绝 | `402` 预算错误、`409` 幂等冲突、重试规则 | [错误码](/zh/api-reference/errors) |
| 无需账户按请求付费 | 在指定的只读 operation 上使用 MPP | [机器支付](/zh/integrations/machine-payments) |

报价与 HTTP 请求中的 `X-AISA-Max-Price-USD` 类似，均会在调用任何提供商之前检查预估费用；但两者都无法限制按计量计费 operation 的最终扣费。控制台中为 key 设置的消费限额才是硬性上限。

**机器支付（MPP）**。在支持 MPP 的 operation 上，未携带凭证的请求会返回带有 `WWW-Authenticate: Payment` 质询的 HTTP `402`；智能体通过 Tempo 完成支付，并携带 `Authorization: Payment <credential>` 发起重试。实时的质询对金额与条款具有最终效力。并非所有端点都支持 MPP，因此请先检查 operation。

| 步骤 | Operation | 报价 | 批准上限 | 结算费用 | 结果已核验 |
| --- | --- | --- | --- | --- | --- |
| 1 | `example_company_enrich` | `<quote A>` | `<cap A>` | `<settled A>` | 是：已返回 Example Corp 的记录 |
| 2 | `example_deep_report` | `<quote B>` | 未批准（超出阈值） | 无 | 已跳过，已询问用户 |

## 防护规则

- **划分不同阶段**：选择、预估、授权、执行、核验支付、核验交付与审计。选择工具绝不代表获得消费许可，成功支付也不能证明交付成功。
- **策略置于提示词之外**。在代码或其他受信任层中强制执行允许的能力、单次调用限制、单任务限制、时间范围限制、确认阈值以及兜底规则。
- **报价不等于批准，未报价更不等于免费**。当 operation、参数或范围发生变化时，必须重新报价。若报价或文档记录的最大上限超过剩余预算，则必须停止执行。
- **仅执行一次并保留标识符**。完整保留请求 ID、用量 ID 与交易 ID。仅在端点文档明确支持时使用幂等键（例如 Similarweb 同步路由）；绝不可为了绕过 `409` 冲突而更换键值。
- **存疑结果对账**：
  - 接纳前被拒绝：修正请求或选择其他 operation。
  - 未确认扣费且无结果：在任何重试前先检查状态。
  - 已记录扣费但结果缺失：先对账或联系支持团队；切勿重复购买。
  - 结果已返回但结算状态不明确：保留该结果并单独核对费用。
  - 网络超时不能证明请求在计费前已经失败。
- **审计时绝不记录机密**。记录任务、决策、operation、批准与结算金额、参考 ID 以及最终结果。切勿存储 API key、钱包私钥、支付凭证或 Bearer token。
- **何时适用更简单的流程**：当用量可预测、采购无需在运行时发生，或者你无法对模棱两可的支付状态对账时，应采用常规的账户充值并由应用程序统一控制调用。
