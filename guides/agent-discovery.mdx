AIsa publishes several machine-readable discovery resources so that autonomous agents can find, understand, and invoke supported capabilities. This guide explains these resources and the end-to-end discovery-to-invocation flow. The rules an agent follows (how to connect, verify, quote, approve spending, and handle errors) live in one place, the [agent setup guide](https://aisa.one/llms.txt); this page only points at it.

## Discovery Endpoints

AIsa exposes the following public URLs for agent and documentation discovery. They require no authentication to read.

| Endpoint | Protocol | URL | Purpose |
| :--- | :--- | :--- | :--- |
| **Agent Card** | Google A2A | `https://aisa.one/.well-known/agent-card.json` | High-level capabilities with metadata, tags, examples, and I/O modes |
| **AI Plugin** | OpenAI Plugin (v1) | `https://aisa.one/.well-known/ai-plugin.json` | Backward compatibility with ChatGPT-era agent tooling |
| **MCP Server** | MCP (Streamable HTTP, OAuth) | `https://mcp.aisa.one/mcp` | The primary endpoint agents connect to, signed in with browser OAuth (clients without a browser send `Authorization: Bearer $AISA_API_KEY` instead). Exposes a few meta tools (`search`, `list_categories`, `batch_get_schema` / `get_details`, `batch_quote`, `batch_use`, `use`, `account`) across the entire catalog. See [Connect via MCP](/agent-quickstart) |
| **MCP Catalog** | Live MCP inventory | `https://mcp.aisa.one/servers` | JSON generated per request by the running MCP service: `serverCount`, `toolCount`, the root and category `entrypoints`, the `modules`, and one record per provider server (`slug`, `docsRef`, `documentHashes`, tool count) plus the loaded `contract` provenance. Counts only: tool names and schemas come from `tools/list` on each endpoint. For listing; connect to `https://mcp.aisa.one/mcp` |
| **OpenAPI Spec** | OpenAPI 3.1.0 | `https://raw.githubusercontent.com/AIsa-team/docs/refs/heads/dev/openapi.yaml` | Machine-readable request and response contracts |
| **MPP Payment Discovery** | OpenAPI 3.1 + `x-payment-info` | `https://dev-api.aisa.one/openapi.json` | Endpoints that accept [machine payments](/integrations/machine-payments) without an API key |
| **Agent setup guide** | llms.txt | `https://aisa.one/llms.txt` | The single rule source for agents: how to connect, verify, use the MCP tools, approve spending, and handle errors |
| **Technical llms.txt** | llms.txt | `https://aisa.one/docs/llms.txt` | Index of this documentation; any page is available as Markdown by appending `.md` to its URL |

## How Agent Discovery Works

The discovery flow follows four steps: **discover**, **connect**, **inspect**, and **invoke**. An autonomous agent starts by reading the agent setup guide and the agent card to learn what AIsa can do, connects over MCP, inspects the exact tool contracts, and invokes quoted calls. Direct HTTP with an API key is the documented fallback for code that cannot speak MCP.

<Steps>
  <Step title="Discover">
    The agent reads the [agent setup guide](https://aisa.one/llms.txt) and fetches `/.well-known/agent-card.json` from `aisa.one`. The card contains a list of skills, each with an `id`, `name`, `description`, `tags`, and `examples`. The agent uses this metadata to determine whether AIsa can fulfill the current task.
  </Step>
  <Step title="Connect (MCP + OAuth, the primary flow)">
    The agent adds `https://mcp.aisa.one/mcp` as a remote MCP server and signs in with browser OAuth; there is no key to paste. Clients without a browser send `Authorization: Bearer $AISA_API_KEY` in the MCP config instead. It then verifies the connection with one free protected call: the `account` operation (or `use` with `{"operation_id": "account"}`). A tool list or a `401` does not count. See [Connect via MCP](/agent-quickstart).
  </Step>
  <Step title="Inspect">
    Over MCP, `search` returns candidate tools with their exact name, arguments schema, and list price, and `batch_get_schema` (also served as `get_details`) returns the full contract for up to 20 tools. The HTTP fallback fetches `/openapi.yaml` instead: parameter types, required fields, authentication requirements, and declared pricing.
  </Step>
  <Step title="Invoke">
    Over MCP, the agent prices the exact calls with `batch_quote` and runs them with `batch_use`, following the [spending rule in the agent setup guide](https://aisa.one/llms.txt) (auto-run when the quote reports `auto_execute_eligible: true`, otherwise one approval message with the quoted total). The HTTP fallback sends the request to `api.aisa.one` with `Authorization: Bearer $AISA_API_KEY` and follows the stricter [direct HTTP rule](/get-started/cli#direct-http-fallback); selected read-only endpoints also accept [MPP payment](/integrations/machine-payments) instead of a key.
  </Step>
</Steps>

## The A2A Agent Card

The [Agent2Agent (A2A) Protocol](https://a2a-protocol.org/latest/) defines a standard format for agents to advertise capabilities and interoperate. AIsa's agent card lives at the well-known URL and describes the platform, authentication requirements, and public capability catalog.

### Fetching the Agent Card

<CodeGroup>

```bash curl
curl -s https://aisa.one/.well-known/agent-card.json | jq .
```

```python Python
import requests

card = requests.get("https://aisa.one/.well-known/agent-card.json").json()
print(f"Agent: {card['name']} — {card['description']}")
print(f"Skills: {len(card['skills'])}")
for skill in card["skills"]:
    print(f"  • {skill['id']}: {skill['name']}")
```

```typescript TypeScript
const res = await fetch("https://aisa.one/.well-known/agent-card.json");
const card = await res.json();
console.log(`Agent: ${card.name} — ${card.description}`);
console.log(`Skills: ${card.skills.length}`);
card.skills.forEach((s: any) => console.log(`  • ${s.id}: ${s.name}`));
```

</CodeGroup>

### Agent Card Structure

The top-level fields describe the agent identity, authentication, and capabilities:

| Field | Type | Description |
| :--- | :--- | :--- |
| `name` | string | Agent name — `"AIsa"` |
| `description` | string | One-line summary of the agent's purpose |
| `url` | string | Base URL for API requests — `https://dev-api.aisa.one` |
| `provider` | object | Organization name and website |
| `version` | string | Semantic version of the agent card |
| `documentationUrl` | string | Link to human-readable documentation |
| `capabilities` | object | Feature flags — streaming, push notifications, state history |
| `authentication` | object | Supported authentication schemes and credential instructions |

### Skill Objects

Each entry in the `skills` array describes a single capability:

| Field | Type | Description |
| :--- | :--- | :--- |
| `id` | string | Unique skill identifier (e.g., `chat-completions`, `twitter-autopilot`) |
| `name` | string | Human-readable skill name |
| `description` | string | What the skill does and what data it provides |
| `tags` | string[] | Searchable tags for filtering and matching |
| `examples` | string[] | Natural-language example queries the skill can handle |
| `inputModes` | string[] | Accepted content types (defaults to `application/json`) |
| `outputModes` | string[] | Response content types (e.g., `application/json`, `text/event-stream`) |

### Available capabilities

The Agent Card is generated from the public catalog. Fetch the live card instead of relying on a fixed capability list in documentation:

```bash
curl -s https://aisa.one/.well-known/agent-card.json \
  | jq -r '.skills[] | [.id, .name, (.tags // [] | join(","))] | @tsv'
```

Use each capability's `description`, `tags`, and `examples` for matching. Confirm the underlying Skill or API documentation before invocation.

## The OpenAI Plugin Manifest

For backward compatibility with agent frameworks that implement the original ChatGPT plugin protocol, AIsa also publishes an `ai-plugin.json` manifest at `/.well-known/ai-plugin.json`. The manifest references the same OpenAPI spec. For current OpenAI tool integration guidance, see [Actions](https://platform.openai.com/docs/actions).

```bash
curl -s https://aisa.one/.well-known/ai-plugin.json | jq .
```

The manifest includes a `description_for_model` field that lists key API endpoints, helping LLM-based agents understand which tools are available without parsing the full OpenAPI spec.

## The OpenAPI 3.1 Specification

The consolidated OpenAPI spec at `/openapi.yaml` is the authoritative machine-readable contract for constructing API requests. Parse the live specification instead of relying on a fixed path or schema count.

### Fetching and Parsing the Spec

<CodeGroup>

```python Python
import yaml, requests

spec = yaml.safe_load(requests.get("https://raw.githubusercontent.com/AIsa-team/docs/refs/heads/dev/openapi.yaml").text)
paths = list(spec["paths"].keys())
print(f"Total endpoints: {len(paths)}")
print(f"First 5: {paths[:5]}")
```

```typescript TypeScript
import YAML from "yaml";

const res = await fetch("https://raw.githubusercontent.com/AIsa-team/docs/refs/heads/dev/openapi.yaml");
const spec = YAML.parse(await res.text());
const paths = Object.keys(spec.paths);
console.log(`Total endpoints: ${paths.length}`);
```

```bash curl
curl -s https://raw.githubusercontent.com/AIsa-team/docs/refs/heads/dev/openapi.yaml | head -50
```

</CodeGroup>

## End-to-End Integration Example (HTTP fallback)

Agents that can speak MCP follow the connect, inspect, and invoke steps above with the `search`, `batch_get_schema`, `batch_quote`, and `batch_use` tools. The following Python example is the HTTP fallback for code that cannot: the agent discovers AIsa's capabilities, identifies the `chat-completions` skill, and makes an authenticated API call. Before a paid call, apply the [approval rule in the agent setup guide](https://aisa.one/llms.txt) and the [direct HTTP rule](/get-started/cli#direct-http-fallback).

```python
import requests

# Step 1: Discover — fetch the agent card
card = requests.get("https://aisa.one/.well-known/agent-card.json").json()

# Step 2: Find a skill by tag
target_tag = "llm"
matching = [s for s in card["skills"] if target_tag in s.get("tags", [])]
if not matching:
    raise RuntimeError(f"No skill found with tag '{target_tag}'")

skill = matching[0]
print(f"Selected skill: {skill['name']} ({skill['id']})")

# Step 3: Invoke — call the API using the base URL from the card
response = requests.post(
    f"{card['url']}/v1/chat/completions",
    headers={
        "Authorization": "Bearer YOUR_AISA_API_KEY",
        "Content-Type": "application/json",
    },
    json={
        "model": "gpt-5.4-mini",
        "messages": [
            {"role": "user", "content": "Summarize the A2A protocol in two sentences."}
        ],
    },
)

result = response.json()
print(result["choices"][0]["message"]["content"])
```

## Authentication

Agents connected through MCP authenticate with browser OAuth, so there is no key to handle; clients without a browser set `Authorization: Bearer $AISA_API_KEY` in the MCP config. The HTTP fallback uses the same Bearer token on every request to `api.aisa.one`:

```
Authorization: Bearer YOUR_AISA_API_KEY
```

Selected read-only endpoints accept [MPP payment](/integrations/machine-payments) instead of a key. A successful `GET /v1/models` is only a transport check; it does not prove authenticated business access. Verify with a free protected call (`account` over MCP, `aisa balance` with the CLI).

Generate an API key from the AIsa console. For detailed key management guidance — scoping, rotation, and secure storage — see the [Authentication](/guides/authentication) guide.

<Warning>
  The discovery resources (`agent-card.json`, `ai-plugin.json`, `openapi.yaml`, `/servers`, and the llms.txt files) are publicly readable and require no authentication. API calls to `api.aisa.one` require the authentication documented for the selected route.
</Warning>

## Integration Patterns

### Pattern 1: Tag-Based Skill Matching

Agents can match tasks to skills using the `tags` array. This is the recommended approach for agents that need to dynamically select capabilities at runtime.

```python
def find_skills_by_tags(card, required_tags):
    """Return skills that match ALL required tags."""
    return [
        skill for skill in card["skills"]
        if all(tag in skill.get("tags", []) for tag in required_tags)
    ]

# Find skills for financial research
finance_skills = find_skills_by_tags(card, ["finance", "stocks"])
# Returns: [MarketPulse Financial Data]
```

### Pattern 2: Example-Based Intent Matching

For LLM-powered agents, the `examples` field provides natural-language queries that can be used for semantic similarity matching against the user's intent.

```python
# Collect all examples with their skill IDs
example_index = []
for skill in card["skills"]:
    for example in skill.get("examples", []):
        example_index.append({"text": example, "skill_id": skill["id"]})

# Use an embedding model to find the closest match to the user's query
# user_query = "What's the stock price of Apple?"
# → Matches MarketPulse skill via "Get the current stock price for AAPL"
```

## CORS Support

The discovery endpoints include permissive CORS headers (`Access-Control-Allow-Origin: *`) so that browser-based agents and web applications can fetch them directly without a proxy server. This applies to:

- `/.well-known/agent-card.json`
- `/.well-known/ai-plugin.json`
- `/openapi.yaml`
