# AIsa Documentation

**The unified resource and transaction network for AI agents.**

AIsa gives agents and developers one programmable interface to discover,
access, and pay for AI models, APIs, real-time data, SaaS tools, and other
digital services.

[Website](https://aisa.one) | [Documentation](https://aisa.one/docs) |
[Console](https://console.aisa.one) |
[API Reference](https://aisa.one/docs/api-reference)

## What AIsa Is

Most digital services are still designed for people: each provider has its own
account, credential, contract, billing model, and integration. That structure
does not scale well for agents that need to discover capabilities and use them
at runtime.

AIsa brings the resource and transaction sides together:

- **Discover:** inspect models, APIs, Skills, and machine-readable capability
  manifests.
- **Access:** use supported resources through a common AIsa credential and
  standard interfaces.
- **Transact:** meter usage and pay per use through account billing or
  supported machine-payment flows.
- **Operate:** review usage, apply spending controls, and add capabilities
  without rebuilding every provider integration.

The model gateway is one AIsa capability, not the whole product. AIsa also
connects agents to live data, search, software tools, reusable Skills, and
payment-enabled services.

## OpenAPI Changes

When changing an OpenAPI source, regenerate a local consolidated spec:

```bash
python3 -m pip install pyyaml
python3 scripts/consolidate_openapi.py --output /tmp/aisa-openapi.yaml
```

`openapi/*.json` files are the source of truth. The root `openapi.yaml` is
generated by the sync workflow and should not be edited directly.

After the generated `openapi.yaml` commit is pushed to `main`, the workflow
sends a `docs_openapi_updated` repository dispatch to
`AIsa-team/aisa-tool-router`. Its payload contains the immutable docs commit,
the consolidated spec SHA-256, the source commit/ref, and the workflow run ID.
The workflow uses the installed `AIsa-team/aisa-release-bot` GitHub App to mint
a short-lived installation token scoped to the private Tool Router repo. The
docs repository must define `TOOL_ROUTER_DISPATCH_APP_ID` as an Actions
variable and store the App PEM in the
`TOOL_ROUTER_DISPATCH_APP_PRIVATE_KEY` Actions secret.
Dispatch runs in a sibling job after the docs revision is captured. Its
`always()` guard lets Tool Router delivery proceed when a later notification
step fails, while a delivery failure cannot roll back the published docs
revision.
If delivery must be retried after the generated file is already current, run
the workflow manually from `main` with `dispatch_tool_router` enabled.

## Contribution Principles

- Lead with the task a developer or agent is trying to complete.
- Distinguish models, Skills, direct APIs, and payment surfaces precisely.
- Document current behavior, authentication, cost, and failure modes without
  implying unsupported guarantees.
- Keep English pages and their `zh/` counterparts aligned when both exist.
- Never commit real API keys, account data, or production response payloads.

## Contract candidate CI and Runtime freshness

Artifact-changing PRs acquire Runtime's public `current` release using
`fetch_runtime_release.py --current`. The importer discovers its exact pins,
verifies the immutable manifest and file hashes, and requires the same fresh
current pointer before and after acquisition. The PR cannot select an older
Runtime release by editing a Docs receipt. Main's last-good Docs acquisition is
not the acquisition pin: Docs may lag Runtime while a source fix is under review,
so requiring that old pin to still be current would block the repair itself.

CI checks the actual committed PR graph against those inputs. It does not
regenerate or rewrite the PR before assessing it. The independently reviewed
coverage baseline, published identity baseline, source-maintenance evidence,
payment binding and formal artifact checks remain required. If Runtime advances
and the PR graph no longer matches, regenerate the complete candidate from a new
verified acquisition, review the diff and rerun CI. Do not alter a formal
publication receipt or accept new pending debt to make the check pass.

The formal publisher separately acquires a fresh release and assesses the exact
staged graph before exporting its publication pointer. Candidate CI success does
not authorize a formal release or assert that consumers have converged.

Runtime payment capabilities may include optional `mpp_methods` and
`x402_methods` lists. Composer keeps the immutable native operation identity and
limits each concrete method's payment flag to the declared uppercase methods.
An empty list disables that surface for every method; an absent list preserves
the previous behavior. Lists never enable a false payment flag. Capability keys,
types and method lists are validated before composition; unknown fields,
duplicate methods and nonstandard or nonuppercase methods are rejected.
These declarations describe payment eligibility, not supplier credential
ownership or successful authentication. They do not waive request-forwarding
checks or grant installed-image, publication or deployment qualification.

```sh
python -m unittest discover -s scripts/tests -p 'test_payment_method_capabilities.py'
```

For mixed request bodies, an explicit Runtime array `items: {}` leaves its
children provider-owned. Composer preserves the reviewed source item schema at
that same array position while keeping Runtime's array type and bounds.
Constrained Runtime items and mismatched source types keep the existing Runtime
override. This changes documentation only, without changing request validation:

```sh
python -m unittest discover -s scripts/tests -p 'test_open_array_items.py'
```

For Runtime-owned query parameters, missing supplier constraints and formats
remain visible as `Provider reference (supplier schema)` guidance in the field
description. The machine-readable schema retains the exact Runtime contract,
including its wire type and defaults. Supplier hints do not add gateway
validation or imply that a supplier default is installed by the gateway.

## Acquire an actual Runtime release for contract review

After the Runtime operator supplies the **actual published artifact revision**
(64 lowercase hex) and deployed compiler Git SHA (40 lowercase hex), acquire its
public immutable files into a new local directory:

```sh
python scripts/fetch_runtime_release.py \
  --base-url https://api.aisa.one \
  --artifact-revision "$ACTUAL_RUNTIME_ARTIFACT_REVISION" \
  --compiler-revision "$DEPLOYED_RUNTIME_COMPILER_SHA" \
  --output "$ACTUAL_COMPLETE_RUNTIME_FACTS"

python scripts/prepare_source_receipts.py \
  --reviewed docs/current-source-review-20261009/merged-source-reviews.json \
  --cache .cache/source-reviews.json

python scripts/check_contract_candidate.py --root "$PWD" \
  --facts-dir "$ACTUAL_COMPLETE_RUNTIME_FACTS" \
  --baseline-ref "$INDEPENDENTLY_REVIEWED_BASELINE_FULL_SHA" \
  --published-ref "$PUBLISHED_DOCS_ARTIFACT_FULL_SHA" \
  --source-receipts .cache/source-reviews.json \
  --report "$READINESS_REPORT"
```

The acquisition command only performs public metadata GETs. It requires a fresh,
unchanged current pointer before and after downloading the exact immutable
manifest; validates its revision, every file SHA/ETag and index/provider binding;
and rejects pending or incomplete selected Runtime coverage. HTTPS verification
is enabled, redirects and environment proxies are disabled, and acquisition is
bounded to 180 seconds, 512 files, 8 MiB per file and 64 MiB per immutable release.
An existing output directory is never reused. Files retain their downloaded
bytes, with both `providers/*.json` and flat copies for the existing Docs CLI.

`category.json` is fetched twice unchanged during that interval and is explicitly
recorded as live, unversioned metadata outside the immutable release manifest.
The receipt records the source/compiler/artifact pins and acquisition time; it
is evidence of input acquisition, **not** Docs publication or baseline approval.
Do not use a hypothetical overlay or historical W0 as the actual Runtime input.

The final command evaluates the current checked-out Docs graph and its offline
recomposition. Existing generated artifacts must still be regenerated through
the normal composition gates, and outstanding request/response definition gaps
remain subject to the strict readiness check. Source review receipts do not
provide the independently approved baseline or prove a code-only Docs commit was
published. See [reviewed source inputs](docs/current-source-review-20261009/README.md).

The loader supports a separately reviewed response-debt identity migration in
`docs/deferred-age-response-rebinding-20261012.json`. The existing c77 input
retains legacy response identities; compiler support alone does not activate the
new identity. Only the separately reviewed exact migration record selects it and
preserves the original
60-item approval bytes and clocks (now 7 request and 53 response gaps). Its 53
enabled and 2 disabled-baseline response identities bind the public operation,
route/method, effective public security and scheme definitions, published
upstream selector/response provenance, selected source and response declarations.
Request parameters/body, opaque Profile revision and pricing are excluded from
that response-only identity. Response/source/route/auth changes still require an
exact approved match; unknown payloads remain explicitly unknown. Old reviewed
input records retain their original identity behavior. Composer and canonical
metadata projection use the same authenticated record; the existing closed
bundle exporter includes that same file, without another registry or Runtime
protocol. This grants no execution or private-provider-auth guarantee.

Focused validation: `python -m unittest discover -s scripts/tests -p "test_response*.py"`
(also `test_deferred_definitions.py` and
`test_canonical_import.py`).

### Formal publication current pointer (same commit)

The existing publication workflow exports `docs/publication/current.json` only
when the complete formal readiness gate passes. New or changed request/response
debts, unknown source maintenance, or missing Runtime inputs prevent publication.
Every composed public URI placeholder must also have a matching required path
parameter with a declared schema or content. Matching Runtime and document
omissions cannot satisfy this check; query parameters with the same name do not
bind URI placeholders. Path Item inheritance, local references and operation
overrides are resolved before checking. This checks URI input completeness, not
supplier execution or business success. Existing pending source debt retains
its separate review requirements.
Failed runs leave the published last-good pointer unchanged. Successful checks
with the same C and unchanged source authorization retain the existing valid
pointer and receipts; observation timestamps alone do not advance main or restart
consumer adoption. New authority evidence, expiry or graph changes still publish
a freshly verified bundle. This does not create another baseline, approval path,
or fallback publication.

CR003 records the user's decision to defer exactly 60 known enabled definition
gaps (10 request, 50 response) in
[`openapi/policies/deferred-enabled-20261010.json`](openapi/policies/deferred-enabled-20261010.json).
The policy has a code-pinned byte hash and participates in the full C file manifest.
It changes release blocking only: the definitions stay pending in coverage and
provider responses. The 10 operations without request/method authority gain no
OpenAPI methods or tools. The 50 operations with proven requests retain their
existing response-pending representation. No schema, routing, price, or provider
authority is inferred by this decision.

CR004 (`CR004-polymarket-relayer-20261019`, `RELAYER_DEFERRAL` in
[`scripts/deferred_definitions.py`](scripts/deferred_definitions.py)) records the
user's 2026-10-19 decision to defer the three Polymarket Relayer operations that
need caller or builder credential headers (`/apis/v1/polymarket/relayer/api/keys`,
`POST /apis/v1/polymarket/submit`, `GET /apis/v1/polymarket/transactions`) until
Services #672 adds the runtime auth descriptors and its Docs counterpart is
ported to main as an ordinary PR. It is code-pinned by content hash, loads with
CR003 (whose bytes are unchanged), and accepts only those three exact
`unforwarded_source_header` request identities for runtime-enabled operations.
The operations are not published as complete: their previously published copies
are retained as disabled `retained_pending` operations, and the other Relayer
operations publish normally.

Readiness reports distinguish `deferred_pending` and `deferred_response_pending`
from the independently reviewed 93 disabled baseline items in `existing_pending`
and `existing_response_pending`. Exact identity, binding, source, reason, status,
and response declaration fingerprints must match; changed or additional gaps
still fail. A response gap on an operation the Runtime reports as `disabled` is
listed in `disabled_response_pending`: it is visible debt that does not block
publication, and because the Runtime status is part of the gap identity it
blocks again as `new_response_pending` the moment the operation is enabled. Each reported gap also carries `runtime_binding` copied from the same
Runtime input (native identity, method, path, status, revision, and public pricing)
for consumer reconciliation; it is evidence, not method or schema authority.
The exporter checks the fixed policy and both report scopes before publishing.
Repairing a deferred definition naturally removes it from the pending output;
its old policy entry does not authorize a different gap.

Unmatched legacy operations keep their historical IDs and descriptions. A known
registry owner (or explicit catalog group) may project `x-aisa-status: disabled`
only when the current Runtime index explicitly excludes that exact valid public
path as disabled. A projected, pending, active or unknown-status Runtime operation
at the same path prevents this projection, including conflicts from another
catalog or HTTP method. Missing Runtime authority and unrelated legacy paths are
left unchanged. Consumers can therefore filter a proven disabled legacy route
without inferring removal from absence alone. The real Twitter Spaces regression
fixture records its immutable Docs and Runtime provenance. Validate this boundary
with `python3 -m unittest discover -s scripts/tests -p test_disabled_legacy.py`
and `python3 -m unittest discover -s scripts/tests -p test_full_registry.py`.

The workflow acquires one fresh immutable release before composition:

```sh
python scripts/fetch_runtime_release.py --current --output /tmp/formal-runtime-facts
python scripts/pull_openapi.py --write --facts-dir /tmp/formal-runtime-facts \
  --baseline-ref "$REVIEWED_BASELINE" --readiness-report /tmp/contract-readiness.json
python scripts/runtime_consolidate_openapi.py --output openapi.yaml
python scripts/check_contract_candidate.py --facts-dir /tmp/formal-runtime-facts \
  --baseline-ref "$REVIEWED_BASELINE" --published-ref "$(git rev-parse HEAD)" \
  --report /tmp/formal-contract-readiness.json
python scripts/export_contract_publication.py --facts-dir /tmp/formal-runtime-facts \
  --report /tmp/formal-contract-readiness.json
```

`contract_release` (C) is SHA-256 of UTF-8 JSON containing exactly
`schema_version`, `runtime`, and `files_sha256`: object keys recursively sorted,
no whitespace, Unicode unescaped. Runtime contains `artifact_revision`,
`source_digest` (R), `compiler_revision`, and `generation`. The file manifest is
the complete `publication_hashes` graph, including the exact sales view
`docs/publication/sales-catalog.json`. Its JSON wrapper contains
`schema_version: 1`, the full `openapi_sha256`, and a compact `document` holding
only published identity, display metadata, server paths, revision, pricing and
Runtime identity bridges. It omits request/response schemas and is never a
replacement authority. The same consolidation command derives it; the formal
check reproduces its exact bytes from the complete graph. `current.sales_catalog`
binds its path and hash, and C includes it in `files_sha256`. The sales page reads
this view plus the same formal report/acquisition instead of parsing the full
schema bundle. The pointer and receipt files under `docs/publication/` remain
outside C to avoid self-referential hashes.
`openapi`, `formal_readiness`, and `runtime_acquisition` each give a repository
relative `path` and exact byte `sha256`. The exporter reproduces source governance from the same attributed receipts
and original assessment time, and compares it against current hashed source
metadata. The formal report binds acquisition bytes
through `runtime_acquisition_sha256` and the same four-field `runtime` identity.
Source authorization is provider scoped. `source_governance.source_scope`
(`schema_version: 1`, `method: operation_source_content_hash`) maps every source
file to the providers whose operations in `openapi/<provider>.json` cite its
`content_hash` through `x-aisa-source` or `x-aisa-response-source.source`
(interned `x-aisa-source-provenance` expanded first). A source cited by no
operation, by a document that is not a `coverage.json` provider, or whose
documents cannot be read maps to `[]` and is **global**. Policy errors, and any
source without a valid review receipt, stay global. Governance `failed` means a
global source is `overdue`/`fetch_failed` or any policy error exists; overdue or
failed attributed sources are listed in `scoped_failures` per provider instead.
`source_authorization_expires_at` is the earliest `review_due_at` or
`next_acquisition_due_at` over global sources only, never an invented publication
TTL; export refuses when it is already due. `provider_authorization_expires_at`
holds one entry per readiness provider: the minimum of that global time and the
due times of the provider's attributed sources, which are never extended and may
already be past. Consumers recompute both fields from the hash-bound report and
stop presenting a provider once its own time passes. A report without
`source_scope` (and a pointer without the provider map) keeps the old meaning:
every source is global.

The pointer, full graph, formal report and acquisition receipt are committed
**together**. The pointer intentionally contains no Docs commit SHA. Consumers
observe `https://raw.githubusercontent.com/AIsa-team/docs/main/docs/publication/current.json`,
resolve current Docs main to its full Git SHA, then read that pinned commit's
pointer, bundle and two receipts. They verify C, all three referenced byte hashes,
the report's exact file manifest, PASS subgates, Runtime identity and source
expiry; they retain C-to-Docs-SHA in their consumption receipt. A changed pointer
between observation and pinned read restarts acquisition. Existing latest-main
consumer guards remain in force. A consumer of the complete `openapi.yaml`
bundle need not download unrelated MDX/localized/upstream files: the producer
checks the full graph and the consumer verifies its canonical manifest and
formal receipt. It must not publish a partial bundle.

Concrete operations carry `x-aisa-runtime-operation` with the original Runtime
`operation_id`, public `path` and uppercase `method` (including `ANY`). This is
copied before public method expansion; it grants no missing request authority
and lets consumers bind public aliases without guessing native identities.

### Website, MCP page, sales catalog and Agent Discovery checks

`check_contract_revisions.py --all-surfaces` also reads the website surfaces
that consumers reach from the publication, with independent codes
(`scripts/public_surface_checks.py`, `check_website_surfaces`). Every read is
bounded and a surface that cannot be read is a `missing_inputs` entry, never a
pass:

- `website-provider-pages`: for every provider id in the publication (aggregate
  `info.x-aisa-document.providers` with a `document_hash`, united with the live
  `/api/sales-api-data` provider ids) `https://aisa.one/api/<id>` must answer
  200 and must not be the soft 404 (`API Not Found` in the HTML title):
  `<id>:not_found`, `<id>:http_<status>`. Exactly one temporary same-origin
  redirect (307/308 with a `Location` on `https://aisa.one`) to such a page
  is accepted and recorded as `{status, location, target}`; otherwise
  `<id>:redirect_offsite` or `<id>:redirect_target_not_found` (any other
  status, a second redirect, or a soft 404 target). One impossible slug must not answer a
  200 page (`unknown-slug:unknown_slug_returns_200`, or
  `unknown-slug:soft_404_returns_200` when it is a 200 soft 404) and the
  retired `image-generation-via-chat` page must not answer 200
  (`image-generation-via-chat:retired_page_returns_200`).
- `website-mcp-page`: the headline counts on `https://aisa.one/mcp` must agree
  with `https://mcp.aisa.one/servers` (`tool_count_mismatch` against
  `toolCount`, `server_count_mismatch` against `serverCount`,
  `category_count_mismatch` against the category entry points), and every
  quoted `$<amount> <operation>` example must equal the sales catalog
  `operations[].quote.amount` (`<name>:example_price_mismatch`,
  `<name>:example_operation_unknown`). `toolCount` is the duplicate-inclusive
  sum of every server's own tool count (a tool pinned under several aliased
  servers counts once per server), not the number of distinct tools reachable
  through `search`; the page's largest tool figure must be that sum. Example
  prices are compared exactly for fixed and usage_based quotes alike, because
  the page derives its figure from the same sales catalog at build time. MCP
  tool names may drop the HTTP method prefix of the operation id.
- `website-sales-catalog`: `/api/sales-api-data` `docs_revision` must be an
  accepted ref (`docs_revision_mismatch`), `contract_release` must equal the
  expected publication pointer (`contract_release_mismatch`), and each
  provider's `endpoint_count` must equal the non-disabled operations the
  hash-bound `docs/publication/sales-catalog.json` attributes to that registry
  provider (`<id>:endpoint_count_mismatch`, `<id>:provider_missing`,
  `<id>:provider_not_in_publication`); operations without a registry provider
  are the website's `models` group.
- `docs-discovery-page`: simple string rules on the rendered body of
  `https://aisa.one/docs/guides/agent-discovery.md` after the generated `>`
  header (`DISCOVERY_PAGE_RULES`): it must link `https://aisa.one/llms.txt` as
  the agent setup guide, must not label it "Product llms.txt", must present
  MCP + OAuth, must keep direct HTTP as the documented fallback and must not
  present Bearer-key requests as the primary flow.
- `website-llms:http_verification_rule_conflict` and
  `website-llms:no_credential_error_rule_conflict`: forbidden-phrase
  regression guards (`WEBSITE_LLMS_RULE_CONFLICTS`), not a positive check of
  the wording. The agent setup guide at
  `https://aisa.one/llms.txt` (served by the website, not from this
  repository) must not state that an authenticated `GET /v1/models` returning
  200 verifies the connection, nor that `401` is the only "not signed in"
  answer; the CLI page and the Errors page table are authoritative.

Offline evidence for these checks lives beside the existing files:
`website-sales-catalog.json`, `mcp-servers.json`, `website-mcp-page.html`,
`docs-discovery-page.md`, and `website-provider-page-<slug>.html` with
optional `website-provider-page-<slug>.status` and `.location` files (a
redirect target is `website-provider-page-<slug>-<target slug>.html`). Validate with
`python -m unittest discover -s scripts/tests -p 'test_website_surface_checks.py'`.

### Upstream maintenance credentials

`refresh-upstream.yml` acquires official automatic sources every 12 hours and
retains hash-bound successful observations in the source-review cache. Source
changes remain a review PR on `automation/upstream-contract-refresh`; this job
does not publish contracts or merge source changes.

PR creation uses the existing `TOOL_ROUTER_DISPATCH_APP_ID` variable and
`TOOL_ROUTER_DISPATCH_APP_PRIVATE_KEY` secret, scoped to the `docs` repository
with Contents and Pull requests write permissions. The App installation must
include `docs` and approve these permissions. The job's `GITHUB_TOKEN` only
needs Contents read. This avoids depending on the separate repository setting
that permits GitHub Actions to create pull requests, and lets the App-created
PR run the existing contract checks.

A successful acquisition alone does not renew published consumer evidence.
The sole `pull-openapi.yml` publisher must assess and export the fresh receipts.
Its scheduled path requires both tracked activation and the operator variable
`RUNTIME_CONTRACT_ACTIVATION_ENABLED=true`; a manual `publish=true` dispatch
uses the same assessment and publication gates. Failed or changed acquisitions
must not be relabeled as an unchanged-source review.

Source maintenance stages the complete proposed graph with the same existing
composer, consolidation and artifact checker before opening a review PR. This
includes generated schemas, pages and sales projection, while the formal
publication pointer and assessment receipts stay unchanged. Missing Runtime
inputs or failed candidate checks prevent an incomplete source PR from being
updated. Only the existing `pull-openapi.yml` publisher exports new formal
receipts after reviewed changes reach main.

The tracked publication plan is ready; the existing operator activation variable
still controls whether scheduled publication and revision monitoring run. No
cadence, receipt lifetime, acceptance baseline or pending policy is relaxed.

### Unified JSON and readable request projection

The Runtime consolidator writes `openapi.yaml` and `openapi/openapi.json` from
one aggregate object. The JSON is excluded from provider input scans to prevent
recursive aggregation, included in the formal file manifest, and checked against
the same offline recomposition. It replaces the old Plant Store placeholder.
Neither this full contract nor its compatibility redirects changes the API
host's `/openapi.json`, which remains the MPP payment subset.

The existing managed MDX block now includes effective method/path, server URL
templates, parameter requiredness, request body, authentication and the reachable
request schema closure. It is ordinary Markdown/JSON so Mintlify's llms-full
output can carry it without expanding OpenAPI frontmatter. Rendering reuses the
compositor's instance-aware reference traversal, preserves native numbers and
recursive schemas, and does not copy response schemas. Historical locale URLs
remain present, with their content refreshed from the current English source.

Deploy and verify the website's `/openapi.json` first, then publish the Docs
root and nested JSON redirects. As with YAML, the oversized JSON is excluded
from Mintlify ingestion; the immutable Git file remains manifest-bound. Root
JSON redirects reuse the existing `redirects` / `permanent` configuration.

Validate with `python -m unittest discover -s scripts/tests -v`, followed by
actual Runtime candidate composition and the formal artifact check. Check live
`llms-full.txt` for the generated request blocks after Mintlify publication;
source Markdown alone does not prove platform rendering. Measure total and
largest generated blocks on the actual candidate. A frozen historical fixture
with duplicate legacy pages produced 7,282 request blocks (22.43 MB total,
75.4 KB largest) before the final renderer review; it is a sizing diagnostic,
not the size or acceptance result of the current live publication.
