<AccordionGroup>
  <Accordion title="Do I need a separate sign-up or plan?">
    No. All AIsa accounts can use AIsa Connect with their existing API key and balance. See [Pricing & limits](/resources/aisa-connect/pricing-and-limits).
  </Accordion>
  <Accordion title="Which apps can my users connect?">
    Browse the live catalog with `GET /apps`, at [aisa.one/catalog/connectors](https://aisa.one/catalog/connectors), or in the [Console](/resources/aisa-connect/console). Apps that need no user account, and platforms AIsa serves through its own [Unified APIs](/resources/unified-apis), are not in the Connect catalog. To ask for an app, use **Request an app** in the Console or write to [developer@aisa.one](mailto:developer@aisa.one).
  </Accordion>
  <Accordion title="How many end users can I connect? Does a higher limit cost more?">
    An AIsa account can have 10,000 active connections by default, counted across all of your end users. To go higher, write to [developer@aisa.one](mailto:developer@aisa.one). Connections themselves are free at any limit; only successful runs are charged. See [Pricing & limits](/resources/aisa-connect/pricing-and-limits#connection-limit).
  </Accordion>
  <Accordion title="Will my users see Google's “unverified app” warning?">
    No. Google apps connect through a verified OAuth app, so users go straight to Google's normal consent screen, and Google's 100-user cap for unverified apps does not apply. The consent screen names the OAuth app AIsa uses for that app, not your product or "AIsa". If that could confuse your users, tell them before they connect.
  </Accordion>
  <Accordion title="Can I call AIsa Connect from a browser or mobile app?">
    Not with an API key. Call it from your backend, and send end users only the `connectUrl` of a hosted session. MCP clients that sign in with OAuth do not need a key.
  </Accordion>
  <Accordion title="How do I test without real users?">
    Connect your own accounts in the [Console](/resources/aisa-connect/console), or pick a test `externalUserId` such as `test_user_1` and follow the [Quickstart](/resources/aisa-connect/quickstart). Test connections count toward your connection limit, so delete them when you are done.
  </Accordion>
  <Accordion title="Do I need to register my redirectUrl with AIsa?">
    No. Pass any HTTPS URL of your app as `redirectUrl` when you start the session, or a `http://localhost` URL while you test locally. Only if you want your account to accept nothing but your own URLs, ask [developer@aisa.one](mailto:developer@aisa.one) for a redirect allowlist. See [Return to your app](/resources/aisa-connect/authorize-users#return-to-your-app).
  </Accordion>
  <Accordion title="Can one end user connect two accounts of the same app?">
    Connecting an app again without `connectionId` can add another connection for the same end user. Runs without `connectionId` use the newest `active` connection for the app; pass `connectionId` to pick a specific one. To refresh an existing connection instead, [reconnect](/resources/aisa-connect/authorize-users#reconnect-a-connection) it with `connectionId`.
  </Accordion>
  <Accordion title="What happens when a user revokes access inside the app?">
    When the app reports that the connection's authorization no longer works, the run fails with `409 reconnect_required` and the connection becomes `needs_reconnect`. Ask the user to reconnect. If the app only refuses that one action for the account, the run returns `400 invalid_request` instead and the connection stays `active`. AIsa does not check connections in the background, so it learns about the change on the next run.
  </Accordion>
  <Accordion title="Does deleting a connection revoke access in the app?">
    Deleting a connection stops AIsa from using it at once: it leaves your lists and runs can no longer use it. Where the app supports it, the OAuth access the user granted is revoked in the app too. For Google this happens when the last active connection that uses the same Google account is deleted: while another one still uses it, for example Gmail and Google Calendar connected separately, the access stays so that connection keeps working. The user can check under **Google Account → Security → Your connections to third-party apps & services**. An API key or other credential the user created in the app is not revoked; the user can remove it in the app.
  </Accordion>
  <Accordion title="Can I get the end user's token and call the app myself?">
    No. No endpoint returns an end user's tokens or keys, and there is no pass-through endpoint for arbitrary app API calls. Use the app's actions.
  </Accordion>
  <Accordion title="Can I use my own OAuth app or brand the hosted page?">
    Not yet. Hosted OAuth uses AIsa's app registrations and AIsa's hosted page.
  </Accordion>
  <Accordion title="Are there triggers or webhooks?">
    Not yet. AIsa does not notify you about events in apps or about finished connect sessions. Poll `GET /connect/sessions/{sessionId}` for connect results.
  </Accordion>
  <Accordion title="Can I limit an agent to read-only actions?">
    Yes, in three ways: expose only actions whose `operationType` is `read` to the model; ask us for an API key limited to read-only Connect access (`connector:read`); and note that Google apps already connect with read-only access in production. See [Guardrails](/resources/aisa-connect/agents#guardrails).
  </Accordion>
  <Accordion title="Why does a write action fail with 400 invalid_request?">
    The message "the app refused this action for the connected account" means the account lacks the permission the action needs. Google apps are read-only in production; for other apps, check the access the user granted or the permissions of their key.
  </Accordion>
  <Accordion title="Can my team share connections?">
    Connections belong to the AIsa account that owns the API key. Every key of that account, and an OAuth sign-in as that account, sees the same connections. There are no per-member or per-connection permissions yet.
  </Accordion>
  <Accordion title="Does AIsa retry failed runs?">
    No. Each run is sent to the app once. To retry safely, send an `Idempotency-Key`; see [Retries and idempotency](/resources/aisa-connect/actions#retries-and-idempotency).
  </Accordion>
  <Accordion title="How many runs can I send per minute?">
    Runs count as writes: 60 per minute per API key, with an account-wide limit across your keys on top. Reads such as the catalog, sessions and connections allow 300 per minute. Over the limit you get `429 rate_limited` with `Retry-After`, and nothing is charged. If your workload needs more, write to [developer@aisa.one](mailto:developer@aisa.one). See [Rate limits](/resources/aisa-connect/pricing-and-limits#rate-limits).
  </Accordion>
  <Accordion title="Is there pagination?">
    The Connect API itself has none: lists return everything in one response, and `GET /apps` takes `limit` up to 5000. Actions that page through app data have their own page fields in `inputSchema`.
  </Accordion>
  <Accordion title="What does an action return?">
    Each action's `outputSchema` from `GET /actions/{actionKey}` describes its `output`. For example, `gmail.fetch_emails` returns `messages`, each with `messageId`, `threadId`, `sender`, `to`, `subject`, `snippet`, `messageTimestamp` and `labelIds`, plus `nextPageToken` when there are more. Read field names from the schema rather than guessing them.
  </Accordion>
  <Accordion title="How long does a connection last?">
    A connection stays `active` until you delete it, or until the app stops accepting its authorization, at which point it becomes `needs_reconnect`. AIsa refreshes OAuth tokens for you, so you never handle token expiry.
  </Accordion>
</AccordionGroup>

Still stuck? See [Errors & troubleshooting](/resources/aisa-connect/errors), or write to [developer@aisa.one](mailto:developer@aisa.one).
